## 四种工作方式与模型

| 工作方式 | 行为与输入 | 模型放在哪里 | STUDIO 当前能力 |
|---|---|---|---|
| Agent | 根据需求理解、规划并调用创作工具，跨节点推进工作；可带附件、技能和生成偏好 | 原站无公开聊天LLM菜单；后台选规划模型，后续图片、视频工具分别选择自己的执行模型 | 已有真实文本/看图对话和持久历史；**尚无画布工具调用循环** |
| 图像 | 直接生成图片：提示词，有参考时还需参考图或其他明确条件 | 原图像模式的 inline 模型菜单与参数菜单 | 当前为明确 TEST MODE；真实生成/编辑能力未配置 |
| 视频 | 直接生成视频；子模式决定文字、首帧、首尾帧、多图、全能参考、视频编辑等输入 | 原视频模式的模型级联菜单与参数菜单 | 当前为明确 TEST MODE；真实视频能力未配置 |
| 动作模仿 | 必填一张角色图和一段动作参考视频，原站限制视频 ≤30s；输出角色动作视频 | 原站此入口未展示自由模型菜单，按专门能力路由；不能塞普通 LLM 型号 | 当前无真实动作迁移能力，通用视频 Mock 不证明支持动作条件 |

**工作方式不是模型型号。** Codex 5.6/6/6.1 是对话模型选择，不能与上述四种方式并列。“图片理解”表示 IMAGE → TEXT/结构化信息，也不是“图像生成”模式。styleCode、sceneCode、presetId 表示业务条件或预设，不自动等于不同模型权重。

原站四项菜单没有 Codex 型号；之前 STUDIO 把型号直接插进该菜单是错误扩展。原站 Agent 的“自动/生成偏好”只配置图片、视频生成偏好，不是聊天 LLM 选择器。随后加入的同工具行聊天型号控件也属于 STUDIO 扩展；按用户“只换模型名字”的严格复刻要求，本轮将其移除。Agent、Frames等无原生LLM菜单的入口采用后台默认策略。

原站已有菜单的型号选项继续来自版本化能力目录，按当前模式、真实输入和输出过滤；不在前端硬编码 Codex 专属列表。以后注册 DeepSeek/千问等真实能力沿用这些菜单和后台策略，仍须通过各功能约束。

当前真实新建选择：TEXT 使用 Codex 5.6/6/6.1；IMAGE 理解使用 6/6.1。5.6 不进入 STUDIO 图片理解候选。旧 `codex-text-v1` / `codex-vision-text-v1` 仅供已有会话兼容。当前没有真实 VIDEO/AUDIO 理解，也没有已开放的真实 IMAGE/VIDEO/AUDIO/3D 生成能力。

## 为什么目录匹配还不够

当前前端与 Go 将视频参考、编辑、延长、动作迁移、片段重拍都合并为 `VIDEO_TO_VIDEO`。`kind + inputKinds + outputKinds` 只能粗筛模态，不能证明支持动作迁移、首尾帧、区域编辑等具体行为。Mock 的广泛输入声明尤其不能作为真实兼容证据。

真实适配前需要版本化支持声明：功能/子模式、conditioning role、参考数量、时长/尺寸限制、参数 schema、输出 schema，以及 stream/session/tools 支持。执行端再次校验；不支持的组合明确拒绝，不能静默丢草图、视频或蒙版，也不能仅追加 system prompt 后宣称支持。

Agent 的媒体生成偏好仍有原生供应商白名单，会排除中立媒体目录；与直接图像/视频菜单不同，真实媒体上线前还需以能力条件替换这段过滤。导演文字/图片入口另需精确 feature/输出 schema 映射，不能仅改旧型号名。

画板手动生成同样提交草图；现 Requirements 把它放入纯文生图 features 的描述需要修正。图像理解与生成的目录、规划 LLM 与执行模型应保持独立。

## STUDIO Agent 现在缺什么

2026-10-06补充：当前原站源码明确声明15类画布工具，普通Agent声明14类；核对证据与本轮上下文/命令切片见 [产品核对](runninghub-agent-product-2026-10-06.md)。画布工具调用循环仍待实现。

已实现：用户隔离、会话和消息持久化，冻结可信提示词，Router session 绑定，真实文本/看图调用、会话续聊、任务查询与事件重放、用量。取消仅在实际支持的状态生效；当前真实 Codex 运行中原生中断尚未接通，不能把停止轮询说成上游已取消。STUDIO 另有带版本的画布保存及 DAG 节点执行机制，可以作为业务工具底座。

本轮CANVAS会话已接入已授权的服务器画布摘要，保存屏障和精确输入字段会先核对；未实现：正式工具规划循环、工具 schema 注册、模型发起工具请求、STUDIO 工具分发/校验/执行、工具结果回传、继续推理与最终画布同步。

证据：Web 助手只输出 `chat.delta/chat.final` 或聊天 WS 事件，工具回执/交互事件会拒绝；STUDIO worker 只轮询模型调用结果；Router Codex 当前关闭原生工具，未知 server request 被拒绝，公开 profile 输出为 TEXT。`executionKind=AGENT` 只是该适配器运行方式，不能作为产品画布 Agent 已完成的依据。现有 tool-results/pending/resume 路径存在预留或拒绝逻辑，不构成可用工具循环。

## 最小画布 Agent 方案（待实现）

STUDIO 管产品与画布：身份、作品归属、节点/连线领域规则、模板、依赖、任务、确认及版本冲突。Router 管模型运行时：模型/Agent profile、工具调用协议、session/turn、事件、用量和适配器，不读 STUDIO 数据库，也不决定业务写权限。

首批白名单工具：

| 工具职责 | 结果 |
|---|---|
| 读取画布和所选节点、查询资产/能力 | 已授权的结构化上下文；资产 ID，不暴露服务器路径或凭据 |
| 创建文本/图片/视频节点、修改允许字段、添加连线 | STUDIO 领域命令；返回新版本、变更及节点 ID |
| 执行一个节点或一组依赖 | 复用已有生成任务，保留所选执行能力、业务模板及参考用途 |
| 查询/等待/取消任务 | 明确任务状态、文字/资产产物、TEST MODE 及错误；取消不支持时如实拒绝；供 Agent 判断下一步 |
| 撤销本轮画布修改 | 以操作回执和预期版本应用反向变更；不撤销已发生的生成调用或费用 |
| 提出计划/请求确认 | 对接原“先询问/自动”语义；无需假造一个已执行的结果 |

一轮：Web 同步当前画布并提交 conversation/project/revision → STUDIO 从已验证身份读取所属作品及该版本快照，编译画布上下文、原业务指令和允许工具 → Router 模型提出 tool call → STUDIO 校验归属/参数/版本，按确认策略执行 → STUDIO 持久化操作与 tool result → Router 恢复该轮 → 循环至完成/取消/步数限制 → Web 按版本应用 STUDIO 已提交的结果。模型参数不能自报身份、授权工具或更改业务权限；普通聊天文本和 nodes[] 也不能直接成为已提交操作。

每个 tool call 要有独立 callRef、逻辑 run/turn 归属、工具版本、参数摘要、幂等键及持久状态，并绑定冻结的模型/参数 schema 与工具目录版本。操作和结果回执同事务保存；重复请求或结果返回原回执，不同摘要冲突。断线先查回执，不重做已执行写入或结果不明的模型调用；人工同时编辑造成 revision 冲突时重新读取/规划。前端未保存编辑先同步，不能用旧快照覆盖人手修改。

需要确认的操作批准前不启动生成；已授权的“自动”策略可直接执行允许范围。确认必须绑定计划/参数摘要和版本，不能由模型批准自己。失败不会伪造成功节点；前端只应用 STUDIO 已提交、同作品且按序可重放的操作，初版可重新读取快照同步。native thread/callback ID、公司登录及服务器路径保留在 Router 私有边界。模型切换继续使用隔离的会话 epoch，不跨模型隐式恢复。

Codex 路线可新增专用工具 Agent profile，通过 app-server 的动态工具请求与回执封装；先核对当前版本协议并实现 Router WAITING_TOOL/工具结果恢复。现有预设及 `studio-authored-1` 指令保持原样；Agent 工具指令用新的版本化模板，不覆盖已有图片解析/剧本等模板。当前文本/看图 profile 保持原行为，不靠开放 shell 或任意文件访问来操作画布。首次工具协议以独立合同扩展标 RESERVED，完成事务、恢复、确认和集成验证后再改 IMPLEMENTED。

开发分两条：先补 STUDIO 业务工具 + Router 工具循环，验证“规划→建节点→连线→执行→回看”；另一路为图片/视频等真实适配器补具体功能约束并逐项验收。文本 Agent 的接通不会自动解决真实出图、视频、动作模仿或实时画板。
