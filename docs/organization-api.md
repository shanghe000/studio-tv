# Project folders and persisted notifications

Implemented in Go/PostgreSQL by `internal/modules/organization`; migration `011_organization.sql`; additive contracts `organization-extension.json` / `.yaml`. Frozen v1 schemas remain unchanged. The composition root supplies the real pool and `protect("tv.access", handler)`. Handlers derive their owner exclusively from the verified server identity, reject team/workspace overrides, and never accept caller owner fields.

Project folders support root/nested listing, creation, rename, recursive deletion, mixed folder/project pages, actual move targets, atomic project creation in folders, and moving a project to a folder or root. The enabled native sorting controls map to actual updated/created/size ascending or descending SQL ordering before pagination. Size means persisted UTF-8 graph bytes plus the byte sizes of active READY assets belonging to the ordinary project; a folder sums descendant ordinary projects. No vendor resource or mock project rows participate.

The product enforces three folder levels and 1,000 active folders per owner in both application and SQL guards. Composite owner foreign keys and active-parent/project guards reject foreign, deleted, internal-vault, or cyclic memberships. Move targets expose real folders and ordinary project leaves, up to 10,000 projects; overflow returns413 instead of a partial target tree. All project queries require actual owner `public.projects` rows with `deleted_at IS NULL AND internal_kind IS NULL`.

Mutation UUID receipts are durable and owner/operation scoped. Their request hash includes the expected revision, so a changed payload or precondition cannot reuse a key. Folder rename/delete, project move, and single notification delete require one strong positive If-Match ETag; missing428, malformed400, stale412 with current revision. Changing membership advances the actual project revision, allowing the existing snapshot save to detect concurrent edits. A no-op move retains the project revision. Source/target ancestors and collection revisions advance transactionally. SQL invalidation triggers also advance folder/collection versions for ordinary core project saves, rename/delete/pin changes, and asset readiness/size changes. Writers take project rows and ancestor folder locks in stable order before comparing revisions.

Folder deletion follows the native confirmation: soft-delete the selected folder, descendant folders, and their current ordinary projects in one transaction. It does not move children to root or erase retained project/asset history. Internal vaults, foreign owners, and projects outside the subtree are untouched. Replay retains the deletion result. Replaying a create receipt for an already-deleted folder/project returns404 and cannot resurrect it.

Notifications support actual paginated type-filtered owner inbox reads, unread counts, batch read, detail, versioned single delete, and atomic bounded batch delete. Every batch ID must be active and owned or the whole operation returns404. Read is idempotent; it advances a notification revision only for an unread row. V1 notification list responses keep the frozen fields; additive v2 lists and detail expose each row's revision. Empty inboxes come from SQL, without official/update fixtures.

The `execution.tasks` terminal-state trigger inserts a GENERATION notification in the same actual task transaction when a task changes to SUCCEEDED, FAILED, or CANCELED. Owner/task uniqueness prevents duplicates. It records the actual task identifier and state, with no model result invention or upstream URL. UPDATE_RECORD and OFFICIAL_MESSAGE appear only when persisted by an actual publisher; this module does not invent release announcements or expose a browser publish endpoint.

Native mapping and exact DTOs are recorded in `.local/iteration-03/organization-seam.md`. Production composition is owned by the root lane. Unit/HTTP tests check strict requests, verified ownership, UUID/revision errors, frozen v1 projection, unavailable failures, unknown404s, and all23 implemented contract routes. Real PostgreSQL tests use only explicit `TEST_DATABASE_URL` and `testdb.New`: each creates, migrates, and drops its own randomly named test database, never the supplied database. Required cases cover concurrent receipts/moves, core invalidation races, SQL ownership/depth constraints, real size pagination, recursive deletion, actual task notifications, read/delete persistence, and PostgreSQL-backed HTTP.
